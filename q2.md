## Question 2

> Configure the cluster to disable **anonymous-auth** in the **kube-apiserver**, and
> delete the ClusterRole `system:user` using the kubeconfig located at `/root/candidate/kubeconfig`.
>
> *(The exam's own note claims "after disabling anonymous-auth your kubectl commands will not work."
> That is **false** — see the correction below. Read the path off your own screen; it is a
> candidate-specific directory.)*

---

### Solution:

#### 🧱 Step 1 — Edit API Server Static Pod

```bash
sudo vim /etc/kubernetes/manifests/kube-apiserver.yaml
```

Add or modify the following flags under `command:`:

```yaml
- --anonymous-auth=false
```

> 💡 Note: add the flag once. Duplicated flags make the API server refuse to start.

Save and exit — the static pod will restart automatically.

---

### ⛔ Correction: kubectl does **not** stop working — verified on a live cluster

The exam note (and most blog write-ups) claim kubectl breaks. It does not. `--anonymous-auth=false`
rejects **unauthenticated** requests; your admin kubeconfig uses a **client certificate**, so it keeps
working normally:

```
$ kubectl get nodes                 # immediately after --anonymous-auth=false
NAME                STATUS   ROLES           AGE   VERSION
cks-control-plane   Ready    control-plane   12m   v1.37.0
cks-worker          Ready    <none>          12m   v1.37.0

$ kubectl auth whoami
Username   kubernetes-admin
Groups     [kubeadm:cluster-admins system:authenticated]
```

**What actually changes** is the API server's own health probes. kubeadm's liveness/readiness probes hit
`/livez` and `/readyz` **anonymously**, so they now get `401`:

```
# anonymous (what the kubelet probe does)   vs   authenticated (what you do)
anon /livez  -> 401                              auth /livez  -> ok
anon /readyz -> 401                              auth /readyz -> ok
anon /healthz-> 401                              auth /healthz-> ok
```

### ⛔ And it gets worse than `0/1 NotReady` — the API server ends up in a crash loop

For the first ~90 seconds the pod merely shows `0/1 Running` with `RESTARTS 0`:

```
$ kubectl -n kube-system get po -l component=kube-apiserver
NAME                               READY   STATUS    RESTARTS   AGE
kube-apiserver-cks-control-plane   0/1     Running   0          53s
```

But the **liveness** probe is what matters. With kubeadm's defaults
(`periodSeconds: 10`, `failureThreshold: 8`) the kubelet gives up after about 90s and **kills the
container as unhealthy** — then restarts it, and kills it again, forever. Measured on a cluster left
running for 30 hours with this flag set:

```
$ crictl ps -a --name kube-apiserver
CONTAINER      STATE    NAME             ATTEMPT
95012381da07f  Exited   kube-apiserver   159        <-- 159 restarts

$ journalctl -u kubelet --since -20min | grep -ciE "Liveness probe failed|Killing container"
26
```

The API server is then only intermittently reachable: it serves for ~90s, gets killed, backs off, comes
back. `kubectl` fails with `Unable to connect to the server: EOF` during the gaps, and the fatal-looking
log tail is just the graceful shutdown — there is **no** startup error to find.

So the honest summary of this task: disabling `--anonymous-auth` on a kubeadm control plane breaks the
kubelet's health checking of the API server. Graders snapshot the flag, so the task still "passes", but
know what you have done to the cluster. If you need the cluster usable afterwards, either take the flag
back off or repoint the probes at something that doesn't require authentication.

---

#### 🧱 Step 2 — Verify Changes (Before kubectl stops working)

Run:

```bash
ps -ef | grep kube-apiserver
```

Ensure you see:

```
--anonymous-auth=false
```

Check that the API server pod is running again:

```bash
kubectl get pods -n kube-system
```

> ⚠️ **Important:** After this change, kubectl commands will no longer work without proper authentication. You'll need to use the kubeconfig file for all subsequent operations.

---

#### 🧱 Step 3 — Test Anonymous Access Blocked

Try an unauthenticated curl:

```bash
curl -k https://localhost:6443/version
```

You should see:

```
Unauthorized
```

That means anonymous-auth is disabled.

---

#### 🧱 Step 4 — Delete the ClusterRole using the provided kubeconfig

Use the kubeconfig the task names (not because kubectl is broken, but because the task says to):

```bash
# Verify the kubeconfig file exists — confirm the exact path on your own screen
ls -la /root/candidate/kubeconfig

# Check the clusterrole exists
kubectl --kubeconfig=/root/candidate/kubeconfig get clusterrole system:user

# Delete it
kubectl --kubeconfig=/root/candidate/kubeconfig delete clusterrole system:user

# Verify it's gone
kubectl --kubeconfig=/root/candidate/kubeconfig get clusterrole system:user
```

> ⚠️ `system:user` is **not** a default Kubernetes ClusterRole — on a stock cluster it does not exist:
> `Error from server (NotFound): clusterroles.rbac.authorization.k8s.io "system:user" not found`.
> The exam seeds it. Read the exact name off your screen; do not assume this one.

Expected output after deletion:
```
Error from server (NotFound): clusterroles.rbac.authorization.k8s.io "system:user" not found
```

---

### 🧠 Summary

* API server now denies any unauthenticated access (`curl -k https://localhost:6443/version` → `401`).
* **kubectl keeps working** — a client-certificate kubeconfig is authenticated, not anonymous.
* Side effect to expect: the kube-apiserver pod reports `0/1 NotReady` because its probes are anonymous —
  and after ~90s the kubelet starts **killing and restarting it in a loop**. Not something to "fix", but
  not harmless either: the cluster becomes intermittently unreachable while the flag is set.
* The `system:user` ClusterRole has been deleted.
