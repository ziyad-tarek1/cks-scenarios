
## Question 6

1. Create a NetworkPolicy that **DENIES all ingress** traffic in namespace `prod`.
2. Create another policy that **allows traffic from pods in namespace prod → pods in namespace data**
   Using **pod labels** + **namespace selectors**.
---

### Solution:

# 🧱 PART 1 — Deny all ingress in namespace `prod`

Namespace must have **default deny** policy.

### **deny-all-ingress.yaml**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress: []
```

# 🧱 PART 2 — Allow pods from `prod` → `data` namespace (ingress allow)

You must:

* Select pods in namespace `data` using **podSelector**
* Allow traffic only from pods in namespace `prod`
  → using **namespaceSelector** with labels
  → AND with podSelector

### **Pre-req:** Add labels to namespaces

```bash
kubectl label namespace prod name=prod --overwrite
kubectl label namespace data name=data --overwrite
```


### **allow-prod-to-data.yaml**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prod-to-data
  namespace: data
spec:
  podSelector:
    matchLabels:
      role: backend   # example: depends on question
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: prod
      podSelector:
        matchLabels:
          app: myapp   # example label from the question
```
---

# 📌 FINAL FORMULA SUMMARY FOR QUESTION 6

### Deny all ingress:

```yaml
podSelector: {}
ingress: []
policyTypes: [Ingress]
```

### Allow traffic from namespace prod:

```yaml
ingress:
- from:
  - namespaceSelector:          # ONE list item => namespaceSelector AND podSelector
      matchLabels:
        name: prod
    podSelector:
      matchLabels:
        app: myapp
```

> ⛔ **The single most common mistake here.** The `-` placement decides AND vs OR:
>
> ```yaml
> - from:                        # AND -> pods labelled app=myapp *in namespace prod*
>   - namespaceSelector: {matchLabels: {name: prod}}
>     podSelector: {matchLabels: {app: myapp}}
> ```
>
> ```yaml
> - from:                        # OR -> ANY pod in prod, PLUS app=myapp in ANY namespace
>   - namespaceSelector: {matchLabels: {name: prod}}
>   - podSelector: {matchLabels: {app: myapp}}
> ```
>
> The task wants **pod labels + namespace selectors** together → use the **AND** form (one list item).

---

### ✅ Validated on a live cluster with real traffic — both policies are correct as written

Applied verbatim against a CNI that enforces NetworkPolicy, with four pods:
`prod/allowed (app=myapp)`, `prod/denied (app=other)`, `data/backend (role=backend)`, `data/inside`.

```
# BEFORE any policy
prod/allowed -> data/backend : 200
prod/denied  -> data/backend : 200

# AFTER both policies
prod/allowed (app=myapp, ns prod) -> backend : 200          <- allowed
prod/denied  (app=other, ns prod) -> backend : timeout      <- blocked (wrong pod label)
data/inside  (same namespace data) -> backend : timeout     <- blocked (not in prod)
data/inside  -> prod/denied:8080                : timeout   <- Part 1 deny-all-ingress works
```

This proves three things that are easy to get wrong:

* `podSelector: {}` + `ingress: []` + `policyTypes: [Ingress]` really is a default-deny for the namespace.
* The AND form correctly rejected `app=other` **from the right namespace**.
* Once a policy selects `role=backend`, **same-namespace** traffic is denied too unless it is listed in
  `from`. `data/inside` was blocked even though it lives in `data`. If the task wants same-namespace
  traffic to keep working, you must add `- podSelector: {}` as a second `from` item.

### ⚠️ Before you start: confirm your CNI enforces NetworkPolicy

A policy that is accepted by the API server but ignored by the CNI looks identical to a correct answer.
Always prove it with traffic:

```bash
kubectl -n prod exec <client> -- curl -s -m 4 -o /dev/null -w '%{http_code}\n' http://<target-pod-ip>
```

Also double-check the namespace labels the policy depends on actually exist:

```bash
kubectl get ns prod data --show-labels
```
