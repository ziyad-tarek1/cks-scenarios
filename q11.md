
## Question 11

> Upgrade the nodes in the cluster to the version given in the task.
>

>
> ```bash
> V=1.34.1          # <-- the version the task actually asks for
> ```

### Solution:

**Reference:**
- https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/

```bash

# First check the controlplane version
# k get no 
# then ssh to the Worker node
# ssh compute-0
# apt-cache madison kubeadm
# apt-cache madison kubelet
# apt-cache madison kubectl

# STEP 1: Cordon the node FIRST (before upgrade) - prevents new pods from being scheduled
# Run this from control plane or any node with kubectl access
kubectl cordon compute-0

# STEP 2: Drain the node - gracefully evicts all pods (respects PodDisruptionBudgets)
# Run this from control plane or any node with kubectl access
kubectl drain compute-0 --ignore-daemonsets --delete-emptydir-data

# STEP 3: Now perform the upgrade ON the node itself (ssh there first)
V=1.34.1

sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm="$V-*"
sudo apt-mark hold kubeadm

kubeadm version -o short            # confirm it is really $V before continuing

# --- WORKER node: ---
sudo kubeadm upgrade node

# --- CONTROL-PLANE node: use `apply` instead, NOT `node` ---
# sudo kubeadm upgrade plan
# sudo kubeadm upgrade apply v$V
# (on any ADDITIONAL control-plane nodes, then use `kubeadm upgrade node`)

sudo apt-mark unhold kubelet kubectl
sudo apt-get update && sudo apt-get install -y kubelet="$V-*" kubectl="$V-*"
sudo apt-mark hold kubelet kubectl

sudo systemctl daemon-reload
sudo systemctl restart kubelet

# STEP 4: After upgrade completes, uncordon the node to make it schedulable again
# Run this from control plane or any node with kubectl access
kubectl uncordon compute-0



```

### ⛔ Two corrections to the original steps

**1. `kubeadm upgrade node` only upgrades a *non-first* node.** The first control-plane node needs
`kubeadm upgrade apply`. Confirmed from `kubeadm upgrade --help` on a live v1.37 cluster:

```
Available Commands:
  apply   Upgrade your Kubernetes cluster to the specified version
  node    Upgrade commands for a node in the cluster
  plan    Check which versions are available to upgrade to ...
  diff    Show what differences would be applied to static pod manifests
```

Order for a whole cluster: **first control-plane (`apply`) → other control-planes (`node`) → workers
(`node`)**. Never upgrade a worker past the control plane.

**2. `apt-mark hold` was missing.** Without re-holding, the next `apt upgrade` silently moves your
kubelet/kubeadm/kubectl off the pinned version. The official docs hold them at every step; the commands
above now do.

### 🔍 Notes

* `kubectl cordon` before `kubectl drain` is harmless but redundant — `drain` cordons first.
* `apt-cache madison kubeadm` only lists what the configured repo offers. Since the
  `pkgs.k8s.io` repos are **per-minor-version**, upgrading across a minor version (e.g. 1.33 → 1.34)
  also means editing `/etc/apt/sources.list.d/kubernetes.list` to point at the new minor:
  ```bash
  sudo sed -i 's|v1\.33|v1.34|' /etc/apt/sources.list.d/kubernetes.list
  sudo apt-get update
  ```
  Without this, `apt-get install kubeadm=1.34.1-*` fails with "Version not found" — a very common stall.
* Verify at the end, from a machine with kubectl:
  ```bash
  kubectl get nodes          # target node shows the new version and is Ready (not SchedulingDisabled)
  ```
