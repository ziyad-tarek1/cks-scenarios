
## Question 16

> Configure Istio service mesh to enforce **mutual TLS (mTLS)** for a specific workload in namespace `my-namespace`.
>
> 1. Enable Istio sidecar injection for the namespace `my-namespace`.
> 2. Create a **PeerAuthentication** resource named `workload-mtls` in namespace `my-namespace` that enforces **STRICT** mTLS mode for pods with label `app: my-app`.

---

### Solution:

**Reference:**
- https://istio.io/latest/docs/tasks/security/authentication/mtls-migration/
- https://istio.io/latest/docs/reference/config/analysis/ist0102/
- https://www.youtube.com/watch?v=MBTMa-yvNSo&list=PLHBCinpJDX3yBb4nJNxoMeWN5pous2Mp5&index=8
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```

Pod-Level mTLS Enforcement Example

```yaml

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: workload-mtls
  namespace: my-namespace
spec:
  # selector => workload level. OMIT it for namespace-wide mTLS.
  selector:
    matchLabels:
      app: my-app
  mtls:
    mode: STRICT
```

> `security.istio.io/v1beta1` also works — both are served — but `v1` is the storage/preferred version
> and is what the object gets normalised to. Verified:
>
> ```
> $ kubectl get crd peerauthentications.security.istio.io -o jsonpath='{...versions}'
> v1       served=true  storage=true
> v1beta1  served=true  storage=false
>
> # applied as v1beta1, stored as:
> $ kubectl -n my-namespace get peerauthentication workload-mtls -o jsonpath='{.apiVersion}'
> security.istio.io/v1
> ```

### ✅ Validated end to end on a live cluster with real traffic

Istio installed (`istioctl install --set profile=minimal`), `my-namespace` labelled, then:

```
# Step 1 check — sidecar injection works (2/2 = app + istio-proxy)
$ kubectl -n my-namespace get po
NAME                           READY   STATUS    RESTARTS   AGE
my-app-75f5fb5fd8-vqzc5        2/2     Running   0          24s
mesh-client-6fc595cfdc-dgzkz   2/2     Running   0          24s
$ kubectl -n plain get po                        # control: no injection
plain-client-67f76c69d4-bkpkl   1/1     Running   0          23s
```

```
# BEFORE PeerAuthentication (Istio default = PERMISSIVE)
plain-client (no sidecar, plaintext) -> my-app : 200
mesh-client  (sidecar, mTLS)         -> my-app : 200

# AFTER applying workload-mtls with mode: STRICT
plain-client (no sidecar, plaintext) -> my-app : curl exit 56   <- BLOCKED
mesh-client  (sidecar, mTLS)         -> my-app : 200            <- still works
```

`curl` exit 56 = "connection reset by peer" — the sidecar dropped the plaintext connection. That is
exactly what STRICT is supposed to do.

### 🔍 Gotchas worth knowing

* **Injection only applies to Pods created *after* the namespace label.** Existing Pods keep running
  without a sidecar and would still accept plaintext. Restart them:
  ```bash
  kubectl label namespace my-namespace istio-injection=enabled
  kubectl -n my-namespace rollout restart deploy
  kubectl -n my-namespace get po        # confirm 2/2, not 1/1
  ```
* **The `selector` is what makes it workload-level.** Remove `selector` and it applies to the whole
  namespace; name it `default` in the root namespace (`istio-system`) and it applies mesh-wide.
* **`selector.matchLabels` must match the *Pod* labels**, not the Service or Deployment labels.
* Verify with:
  ```bash
  kubectl -n my-namespace get peerauthentication
  istioctl analyze -n my-namespace
  ```
* Newer Istio installs may use the **ambient** data plane, where the label is
  `istio.io/dataplane-mode=ambient` rather than `istio-injection=enabled`. Check which the cluster uses
  (`kubectl -n istio-system get pods`) — `istio-injection` is the sidecar mode this task describes.
