
## Question 12

1. Create a TLS secret using a given key + cert file
2. Create an Ingress that uses that TLS secret
3. Add a host (given in the exam)
4. Test using curl
---

### Solution:
# ✅ Step 1 — Create TLS Secret (using provided `cert.crt` & `cert.key`)

```bash
kubectl create secret tls tls-secret \
  --cert=/path/to/cert.crt \
  --key=/path/to/cert.key \
  -n your-namespace
```

If namespace is not specified in the question → use `default`.

---

# ✅ Step 2 — Create an Ingress using TLS

Example host from exam: `app.example.com`

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  namespace: your-namespace
spec:
  ingressClassName: nginx        # omit only if an IngressClass is marked default
  tls:
    - hosts:
        - app.example.com
      secretName: tls-secret
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: myapp-svc
                port:
                  number: 80
```

Apply:

```bash
kubectl apply -f ingress.yaml
```

# ✅ Step 3 — Test Using curl (IMPORTANT FOR CKS)

If self-signed: use `-k`:

```bash
curl -k https://app.example.com
```

If DNS is not resolvable, **don't** use the `/etc/hosts` one-liner that reads
`{.status.loadBalancer.ingress[0].ip}` — verified on a live cluster, that field is frequently **empty**:

```
$ kubectl get ing myapp-ingress -o jsonpath='{.status}'
{"loadBalancer":{}}
$ kubectl get ing myapp-ingress
NAME            CLASS   HOSTS             ADDRESS   PORTS     AGE
myapp-ingress   nginx   app.example.com             80, 443   11s
                                          ^^^^^^^ empty
```

It is only populated when something actually assigns an address (a cloud LoadBalancer, or MetalLB). On a
bare-metal/NodePort/hostPort controller it stays empty, and the one-liner appends a **broken**
`/etc/hosts` line (` app.example.com`) that silently breaks name resolution.

**Use `--resolve` instead — no `/etc/hosts` edit, no dependency on `.status`:**

```bash
curl -k --resolve app.example.com:443:127.0.0.1 https://app.example.com/
```

Or resolve to the node IP / the controller's Service, whichever is reachable:

```bash
# find a real target
kubectl -n ingress-nginx get svc ingress-nginx-controller
kubectl get nodes -o wide                     # node INTERNAL-IP

curl -k --resolve app.example.com:443:<NODE_IP> https://app.example.com/
```

If you do need `/etc/hosts`, write the IP yourself rather than from `.status`:

```bash
echo "<NODE_IP> app.example.com" | sudo tee -a /etc/hosts
```

### ✅ Validated end to end on a live cluster

With ingress-nginx installed and a `myapp-svc` backend:

```
$ curl -sk --resolve app.example.com:443:127.0.0.1 -o /dev/null -w '%{http_code}\n' https://app.example.com/
200

# and the cert served is genuinely the one from the Secret:
$ echo | openssl s_client -connect 127.0.0.1:443 -servername app.example.com 2>/dev/null \
    | openssl x509 -noout -subject -issuer
subject=CN=app.example.com
issuer=CN=app.example.com
```

### 🔍 On `ingressClassName`

It worked in this test *even without* `ingressClassName`, but only because that controller runs with
`--watch-ingress-without-class=true`:

```
$ kubectl -n ingress-nginx get deploy ingress-nginx-controller -o jsonpath='{...args}'
"--controller-class=k8s.io/ingress-nginx"
"--ingress-class=nginx"
"--watch-ingress-without-class=true"
```

That is **not** guaranteed, and no IngressClass was marked default:

```
$ kubectl get ingressclass -o custom-columns=NAME:.metadata.name,DEFAULT:'.metadata.annotations.ingressclass\.kubernetes\.io/is-default-class'
NAME    DEFAULT
nginx   <none>
```

So always set `ingressClassName` explicitly. Check what's available with `kubectl get ingressclass`.

### 🔍 If `curl` returns the wrong cert ("Kubernetes Ingress Controller Fake Certificate")

The controller fell back to its self-signed default, meaning TLS didn't bind. Usual causes:

* the Secret is in a **different namespace** than the Ingress (they must match),
* a typo in `secretName`,
* the `host` in `spec.tls[].hosts` does not match the `host` in `spec.rules[]`,
* you didn't pass SNI (`--resolve`/`-H Host:` alone isn't enough — use `--resolve`).
