# ✅ **Step 2 — Use Falco to detect writes to `/dev/mem`**

Falco has an official rule detecting this behavior:

---

## 📘 **Falco rule reference**

> ⛔ **Corrected.** There is **no** built-in Falco rule named "Write below /dev" or "Write to special
> files like /dev/mem". Verified against the official rulesets — `/dev/mem` does not appear anywhere:
>
> ```
> $ grep -n "/dev/mem" falco_rules.yaml falco-incubating_rules.yaml
> (no matches)
>
> $ grep -nE "^- rule:" falco_rules.yaml falco-incubating_rules.yaml | grep -iE "dev|mem"
> falco_rules.yaml:1172:            - rule: Execution from /dev/shm
> falco_rules.yaml:1266:            - rule: Fileless execution via memfd_create
> falco-incubating_rules.yaml:842:  - rule: Create files below dev
> ```
>
> The closest built-in is **`Create files below dev`** (in the *incubating* ruleset, so often not loaded),
> and it fires on **create**, not **write**. For this task you write your own rule — which is what the
> snippet below does.

Rule file locations:

* `/etc/falco/falco_rules.yaml` — the default ruleset (macros/lists live here)
* `/etc/falco/rules.d/` — drop-in custom rules
* `/etc/falco/falco.yaml` — config, including which `rules_files` get loaded

Custom rule (validated with `falco --validate`):

```yaml
- rule: Write to dev mem
  desc: Detect any write attempt to /dev/mem
  condition: evt.type=write and fd.name=/dev/mem
  output: "Write to /dev/mem detected (user=%user.name ns=%k8s.ns.name pod=%k8s.pod.name container=%container.name)"
  priority: CRITICAL
```

Include `%k8s.ns.name` and `%k8s.pod.name` — the pod name is the whole point of the task, and the
namespace is what lets you find the Deployment afterwards.

# ✅ **Step 3 — Run Falco and identify the pod**

**Note:** Falco may not be installed as a service. Use `falco -U` for monitoring.

Start Falco and monitor output:

```bash
# Primary method (if Falco is not installed as a service)
sudo falco -U

# Alternative (if Falco IS running as a service)
sudo journalctl -u falco -f
```

> ### ⛔ Careful with `-r` — it **replaces** the ruleset, it does not add to it
>
> `sudo falco -r /etc/falco/rules.d/falco_custom.yaml -U` loads **only** that file. Any macro or list the
> custom rules reference (they almost always reference some) is then undefined and Falco **exits**.
> Verified:
>
> ```
> $ falco -r custom.yaml --validate custom.yaml
> rule 'Package management process launched': (custom.yaml:6:2)
> condition expression: ("package_mgmt_procs":7:3)
> ------
> package_mgmt_procs
>                  ^
> ------
> LOAD_ERR_VALIDATE: Undefined macro 'package_mgmt_procs' used in filter.
> ```
>
> (`package_mgmt_procs` is defined in the shipped rulesets, not in the custom file.)
>
> **Safest: pass no `-r` at all** and let Falco load everything from `falco.yaml`'s `rules_files:`,
> which already includes `/etc/falco/rules.d/`:
>
> ```bash
> sudo falco -U
> ```
>
> If you must use `-r`, list the base ruleset **first**, then your file:
>
> ```bash
> sudo falco -r /etc/falco/falco_rules.yaml -r /etc/falco/rules.d/falco_custom.yaml -U
> ```
>
> And validate before you rely on it (pass every file in one command, or they're checked in isolation):
>
> ```bash
> sudo falco --validate /etc/falco/falco_rules.yaml --validate /etc/falco/rules.d/falco_custom.yaml
> ```

Expected alert:

```
Write to /dev/mem detected (pod=ollama-deploy-2-xxx container=ollama)
```

This gives you:

* Pod name
* Deployment name
* Container name

## **Task 2: Find nginx Pod Triggering "Package management process launched"**

### Step 1 — Modify the Falco rule log format

Edit the custom rules file:

```bash
sudo vim /etc/falco/rules.d/falco_custom.yaml
```

Find the rule "Package management process launched" and change **only** its `output` field:

```yaml
- rule: Package management process launched
  desc: Detect package management processes
  condition: package_mgmt_procs
  output: "Package management process launched %evt.time, %container.id, %container.name, %user.name"
  priority: WARNING
```

> ### ⛔ `%evt.time.s` is the **wrong field** — it strips the nanoseconds
>
> The task asks for *time-with-nanoseconds*. Straight from `falco --list`:
>
> ```
> evt.time          event timestamp as a time string that includes the nanosecond part.
> evt.time.s        event timestamp as a time string with no nanoseconds.
> evt.time.iso8601  event timestamp in ISO 8601 format, including nanoseconds and time zone offset (in UTC).
> evt.rawtime       absolute event timestamp, i.e. nanoseconds from epoch.
> ```
>
> `evt.time.s` is explicitly the **no-nanoseconds** variant. Use **`%evt.time`** (or `%evt.time.iso8601`).
> This one character costs the whole task.
>
> Also note the task says *"change the log text **after** 'Package management process launched'"* — so
> keep that prefix in the output string and replace only what follows it.

Save the file, then validate before restarting:

```bash
sudo falco --validate /etc/falco/falco_rules.yaml --validate /etc/falco/rules.d/falco_custom.yaml
# => Ok  (a LOAD_NO_EVTTYPE performance warning on this rule is expected and harmless)
```

### Step 2 — Restart Falco to apply changes

**Note:** Falco may not be installed as a service. If running directly, stop with Ctrl+C and restart.

If Falco is running as service:

```bash
sudo systemctl restart falco
```

If running Falco directly:

```bash
# Stop current Falco process (Ctrl+C)
# Restart with updated rules
sudo falco -r /etc/falco/rules.d/falco_custom.yaml -U
```

### Step 3 — Monitor Falco logs for nginx pod

**Note:** Use `falco -U` for monitoring if Falco is not installed as a service.

```bash
# Primary method: Run Falco directly with custom rules
sudo falco -r /etc/falco/rules.d/falco_custom.yaml -U | grep -i "nginx\|package"

# Alternative (if Falco is running as service)

```

From `cks7262`:

```bash

# Get the Deployment name

### Step 7 — Verify the log file format

```bash
# On cks7262
cat /opt/course/2/falco.log
```

The log should contain entries in the format:

```
Package management process launched 10:30:45.123456789, abc123def456, nginx-container, root
```

Each line must have: `time-with-nanoseconds, container-id, container-name, user-name`.

**Check the nanoseconds are actually there** — if you see `10:30:45` with no fractional part, you used
`%evt.time.s` and the answer is wrong:

```bash
grep -c '\.[0-9]\{9\}' /opt/course/2/falco.log     # expect: > 0
```

Also sanity-check the file is not empty and not full of startup noise:

```bash
wc -l /opt/course/2/falco.log
head -3 /opt/course/2/falco.log
```

### 🔍 Part 1 — a faster way to find the offending pod

Falco is the right answer to "which tool", but you still have to map a container back to a Deployment:

```bash
# from the Falco alert you get container.id / container.name / k8s.pod.name
kubectl get po -A -o wide | grep <pod-name>
kubectl get po <pod> -n <ns> -o jsonpath='{.metadata.ownerReferences[0].name}'   # -> ReplicaSet
kubectl get rs <rs> -n <ns> -o jsonpath='{.metadata.ownerReferences[0].name}'    # -> Deployment
kubectl scale deploy <deployment> -n <ns> --replicas=0
```

Note the Pod's owner is the **ReplicaSet**, not the Deployment — one extra hop that trips people up.
`kubectl get po <pod> -o jsonpath='{.metadata.ownerReferences[0].name}'` returns something like
`ollama-deploy-2-7f48bb4856`; strip the last hash segment to get the Deployment name, or do the two-step
lookup above.
